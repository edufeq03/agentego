================================================================
ANÁLISE TÉCNICA E ESTRATÉGICA — ATENDIA (agente_academia)
Projeto: SaaS de Agentes de Atendimento/Qualificação/Venda
Data: Maio 2026
================================================================

CONTEXTO DO PROJETO
-------------------
O projeto é um SaaS multi-tenant que provisiona agentes de IA
para atendimento via WhatsApp (Evolution API), com dashboard
em Next.js 15, backend em FastAPI/Python e banco PostgreSQL.
A arquitetura está bem fundamentada: buffer de debounce, pipeline
de funil, transbordo humano, relatórios semanais e configuração
dinâmica por nicho. A análise abaixo foi feita sobre o código-fonte
real e está dividida em três eixos e organizada em sprints de
implementação.

EIXOS ANALISADOS
-----------------
1. Segurança de Dados e da Aplicação
2. Melhorias de Modelo de Negócio
3. Melhorias de Usabilidade

================================================================
SPRINT 1 — SEGURANÇA CRÍTICA (Prioridade Máxima)
================================================================

OBJETIVO: Corrigir vulnerabilidades que comprometem a aplicação
em produção antes de qualquer nova funcionalidade.

---
ITEM 1.1 — Admin Token hardcoded com valor padrão inseguro
---
ARQUIVO: bot-service/app/admin_api.py
PROBLEMA ENCONTRADO:
  ADMIN_TOKEN = os.getenv("ADMIN_TOKEN", "atendia-master-2026")
  O fallback "atendia-master-2026" é um segredo público no código.
  Qualquer pessoa com acesso ao repositório pode chamar /api/admin/*
  com esse token e criar empresas, deletar dados, impersonar clientes.

SOLUÇÃO:
  - Remover o valor padrão do fallback. Se ADMIN_TOKEN não estiver
    definido no ambiente, a aplicação NÃO deve subir.
  - Validar na inicialização:
    ADMIN_TOKEN = os.getenv("ADMIN_TOKEN")
    if not ADMIN_TOKEN:
        raise RuntimeError("ADMIN_TOKEN não definido. A aplicação não pode iniciar.")

---
ITEM 1.2 — Logging do token de admin em texto claro
---
ARQUIVO: bot-service/app/admin_api.py
PROBLEMA ENCONTRADO:
  logger.info(f"Tentativa de login ADM com token: {x_admin_token}")
  logger.warning(f"Acesso Negado! Esperado: {ADMIN_TOKEN} | Recebido: {x_admin_token}")
  O token esperado é logado em warning. Qualquer sistema de log
  centralizado (Datadog, Loki, etc.) vai guardar isso.

SOLUÇÃO:
  - Nunca logar o valor do ADMIN_TOKEN esperado.
  - Usar apenas: logger.warning("Acesso negado: token de admin inválido.")
  - Remover o comentário "Removeremos depois" — remover agora.

---
ITEM 1.3 — JWT_SECRET com fallback inseguro
---
ARQUIVO: bot-service/app/auth.py
PROBLEMA ENCONTRADO:
  SECRET_KEY = os.getenv("JWT_SECRET", "super_secret_key_change_in_production")
  O fallback é público e amplamente conhecido (é um exemplo didático).
  Tokens forjados com essa chave serão aceitos como válidos.

SOLUÇÃO:
  SECRET_KEY = os.getenv("JWT_SECRET")
  if not SECRET_KEY or len(SECRET_KEY) < 32:
      raise RuntimeError("JWT_SECRET não definido ou muito curto.")

---
ITEM 1.4 — Credenciais do banco hardcoded no docker-compose
---
ARQUIVO: docker-compose.yml
PROBLEMA ENCONTRADO:
  POSTGRES_USER: user
  POSTGRES_PASSWORD: pass
  E também no fallback de DATABASE_URL em database.py:
  "postgresql://user:pass@localhost:5432/atendimento"
  Credenciais de produção nunca devem estar no código-fonte.

SOLUÇÃO:
  - No docker-compose.yml, usar variáveis de ambiente:
    POSTGRES_USER: ${POSTGRES_USER}
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
  - Adicionar POSTGRES_USER e POSTGRES_PASSWORD ao .env.example
    com instruções claras.
  - Remover o fallback hardcoded do database.py. Se DATABASE_URL
    não existir, a aplicação não deve iniciar.

---
ITEM 1.5 — Endpoint de transbordo sem autenticação
---
ARQUIVO: bot-service/app/main.py
PROBLEMA ENCONTRADO:
  @app.delete("/transbordo/{token}/{telefone}")
  def reativar_robo(token: str, telefone: str):
  Este endpoint usa o webhook_token como "autenticação". O webhook_token
  é exposto no dashboard para o cliente copiar e configurar na Evolution.
  Qualquer pessoa que conheça o token pode reativar o robô de qualquer
  conversa pausada.

SOLUÇÃO:
  - Esse endpoint deve exigir o JWT de autenticação do dashboard,
    não o webhook_token.
  - O webhook_token deve ser usado APENAS pelo webhook da Evolution.
  - Mover a lógica de reativação para um endpoint autenticado em
    dashboard_api.py (já existe /conversas/{telefone}/reativar lá).
  - Avaliar se o endpoint DELETE /transbordo/{token}/{telefone} deve
    continuar existindo — se sim, protegê-lo com JWT.

---
ITEM 1.6 — conversas.db (SQLite) commitado no repositório
---
ARQUIVO: agente_academia-main/conversas.db (na raiz do ZIP)
PROBLEMA ENCONTRADO:
  Um arquivo de banco de dados com dados reais está no repositório.
  Mesmo que seja de testes, pode conter números de telefone reais,
  mensagens de clientes, etc.

SOLUÇÃO:
  - Adicionar *.db ao .gitignore imediatamente.
  - Apagar o arquivo do histórico git (git filter-repo ou BFG).
  - Verificar se há dados reais no arquivo antes de descartar.

SPRINT 2 — SEGURANÇA COMPLEMENTAR
================================================================

OBJETIVO: Proteções secundárias que reduzem superfície de ataque
e aumentam robustez em produção.

---
ITEM 2.1 — Rate limiting no webhook e endpoints públicos
---
ARQUIVO: bot-service/app/main.py
PROBLEMA:
  O endpoint /webhook/{token} não tem rate limiting. Um atacante pode
  bombardear o endpoint com mensagens fictícias, gerando custos na
  API da OpenAI e poluindo o banco de dados.

SOLUÇÃO:
  - Adicionar slowapi (rate limiting para FastAPI) ao requirements.txt.
  - Limitar /webhook/{token} a, por exemplo, 60 req/min por IP.
  - Limitar /api/dashboard/login a 10 tentativas/min por IP (proteção
    contra brute force de senhas).

---
ITEM 2.2 — Tamanho máximo de payload no webhook
---
ARQUIVO: bot-service/app/main.py
PROBLEMA:
  Não há validação do tamanho do corpo da requisição no webhook.
  Uma mensagem de áudio com base64 muito grande pode travar o worker.

SOLUÇÃO:
  - Definir um limite máximo de tamanho de payload via middleware:
    app.add_middleware(ContentSizeLimitMiddleware, max_content_size=10_000_000)
  - Biblioteca: starlette-wtf ou implementar middleware customizado.

---
ITEM 2.3 — CORS muito permissivo nos métodos
---
ARQUIVO: bot-service/app/main.py
PROBLEMA:
  allow_methods=["*"] e allow_headers=["*"] expõem todos os
  métodos HTTP (incluindo DELETE, PATCH, etc.) para todos os
  domínios listados.

SOLUÇÃO:
  - Restringir para os métodos que o frontend realmente usa:
    allow_methods=["GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS"]
  - Restringir allow_headers para os cabeçalhos necessários:
    allow_headers=["Authorization", "Content-Type", "X-Admin-Token"]

---
ITEM 2.4 — Ausência de validação do número de telefone
---
ARQUIVO: bot-service/app/main.py (webhook)
PROBLEMA:
  O telefone extraído do payload da Evolution não é validado.
  Um payload malformado pode injetar strings arbitrárias como
  telefone no banco de dados.

SOLUÇÃO:
  - Validar que o telefone contém apenas dígitos (regex: r'^\d{10,15}$').
  - Rejeitar webhooks com telefone inválido antes de tocar o banco.

---
ITEM 2.5 — Tokens de acesso com expiração de 7 dias sem refresh token
---
ARQUIVO: bot-service/app/auth.py
PROBLEMA:
  ACCESS_TOKEN_EXPIRE_MINUTES = 60 * 24 * 7 (7 dias)
  Se um token for comprometido, o atacante tem acesso por até 7 dias.
  Não existe mecanismo de refresh ou revogação.

SOLUÇÃO DE CURTO PRAZO:
  - Reduzir para 24 horas ou 8 horas.
  - Implementar lógica de refresh token (endpoint /dashboard/refresh).

SOLUÇÃO DE MÉDIO PRAZO:
  - Adicionar tabela de tokens revogados (blacklist) ou usar Redis
    para invalidação sob demanda (quando o admin desativa uma empresa).

SPRINT 3 — MODELO DE NEGÓCIO: CONTROLE E MONETIZAÇÃO
================================================================

OBJETIVO: Adicionar os mecanismos necessários para que o SaaS
funcione de forma sustentável e escalável comercialmente.

---
ITEM 3.1 — Bloqueio automático de empresa após expiração do trial
---
PROBLEMA:
  O campo data_expiracao_teste existe no banco, mas não há nenhum
  código que bloqueie o acesso quando a data expira. O campo ativo
  precisa ser atualizado manualmente pelo admin.

SOLUÇÃO:
  - Criar uma tarefa agendada (APScheduler, já está instalado) que
    rode diariamente às 02:00 e desative empresas com trial expirado.
  - No middleware de autenticação (obter_empresa), verificar se
    data_expiracao_teste < agora E empresa não pagou. Se sim, retornar
    HTTP 402 com mensagem clara.
  - Tarefa sugerida em main.py:
    async def tarefa_expirar_trials():
        db = SessionLocal()
        agora = datetime.now()
        empresas = db.query(Empresa).filter(
            Empresa.data_expiracao_teste < agora,
            Empresa.ativo == True
        ).all()
        for e in empresas:
            e.ativo = False
        db.commit()
        db.close()
    scheduler.add_job(tarefa_expirar_trials, 'cron', hour=2, minute=0)

---
ITEM 3.2 — Ausência total de controle de uso (tokens OpenAI)
---
PROBLEMA:
  Não há tracking de consumo de tokens por empresa. Um cliente em
  plano básico pode gerar o mesmo custo de API que um cliente enterprise.
  Isso torna a precificação impossível de calibrar.

SOLUÇÃO:
  - Adicionar coluna tokens_consumidos_mes (Integer) na tabela Empresa
    ou criar tabela UsoMensal(empresa_id, ano, mes, tokens).
  - Na função perguntar() de openai_client.py, capturar
    response.usage.total_tokens e registrar no banco.
  - Criar endpoint no admin_api: GET /admin/uso-mensal para visualização.
  - No futuro: definir limites por plano e pausar empresa ao atingir teto.

---
ITEM 3.3 — Campo cupom_vendedor sem lógica associada
---
PROBLEMA:
  O campo cupom_vendedor existe no modelo Empresa e na tela de criação
  do admin, mas não há lógica que calcule comissão, aplique desconto
  ou gere relatório por vendedor.

SOLUÇÃO:
  - Criar tabela Vendedor(id, nome, cupom, email, comissao_pct).
  - Na criação de empresa, vincular ao vendedor pelo cupom.
  - Endpoint admin: GET /admin/vendedores/{cupom}/empresas → lista
    de empresas captadas e valor de mensalidade associado.
  - Isso habilita o modelo de revenda/afiliados que é padrão em SaaS B2B.

---
ITEM 3.4 — Plano/tier da empresa não existe no modelo
---
PROBLEMA:
  Só existe valor_mensalidade (float). Não há conceito de plano
  (básico, pro, enterprise) que permita restringir funcionalidades
  por nível. Isso impede qualquer estratégia de upsell.

SOLUÇÃO:
  - Adicionar coluna plano (String: "trial", "basico", "pro", "enterprise")
    na tabela Empresa.
  - Definir limites por plano (ex: leads máximos, instâncias WhatsApp,
    uso de áudio) e aplicar nas validações.
  - O dashboard pode exibir o plano atual e um CTA de upgrade.

---
ITEM 3.5 — Sem histórico de pagamentos
---
PROBLEMA:
  Não há registro de quando e quanto cada empresa pagou. Impossível
  fazer cobrança recorrente, gerar NF ou auditar inadimplência.

SOLUÇÃO DE CURTO PRAZO:
  - Criar tabela Pagamento(id, empresa_id, valor, data, status,
    referencia_externa).
  - Preencher manualmente via admin_api quando o pagamento for confirmado.

SOLUÇÃO DE MÉDIO PRAZO:
  - Integrar Stripe ou Asaas (popular no Brasil) para cobrança
    recorrente automatizada. O webhook do gateway atualiza a tabela
    Pagamento e reativa/desativa a empresa automaticamente.

================================================================
SPRINT 4 — MODELO DE NEGÓCIO: PRODUTO E DIFERENCIAÇÃO
================================================================

OBJETIVO: Funcionalidades que aumentam o valor percebido pelo
cliente (empresa/negócio) e reduzem churn.

---
ITEM 4.1 — Página de configurações travada em nicho de academia
---
ARQUIVO: dashboard/src/app/(dashboard)/[slug]/configuracoes/page.tsx
PROBLEMA:
  O frontend de configurações usa uma interface tipada para academia
  (planos: {basico, vip}, horarios: {semana, sabado}, professores[]).
  O backend já suporta configuração genérica (campo config JSONB),
  mas o frontend não acompanhou. Um cliente de imobiliária, clínica
  ou pet shop recebe uma tela de academia.

SOLUÇÃO:
  - Refatorar a página de configurações para ser orientada a seções
    dinâmicas baseadas no template do nicho.
  - Estrutura sugerida no JSONB de config:
    {
      "identidade": {nome_agente, cargo, nome_empresa, missao, tom_voz},
      "conhecimento": {[titulo_secao]: [itens]},
      "regras": ["regra 1", "regra 2"],
      "horarios": "texto livre"
    }
  - O frontend renderiza seções com base nas chaves de "conhecimento",
    permitindo adicionar/remover seções livremente.
  - Isso é essencial para o posicionamento multi-nicho do produto.

---
ITEM 4.2 — Classifier de intenção é frágil e limitado
---
ARQUIVO: bot-service/app/classifier.py
PROBLEMA:
  O classificador usa matching de substring simples. Palavras como
  "planejamento" vão acionar "plano". Não há fallback semântico.
  O stage do funil depende diretamente desse classificador, então
  erros aqui poluem o funil de vendas do cliente.

SOLUÇÃO DE CURTO PRAZO:
  - Adicionar limites de palavras (verificar palavra completa, não substring).
  - Usar re.search com word boundaries: re.search(r'\bplano\b', texto).
  - Expandir o vocabulário de cada intenção com mais variações regionais/PT-BR.

SOLUÇÃO DE MÉDIO PRAZO:
  - Mover a classificação para a própria IA (OpenAI):
    Pedir ao modelo que retorne a intenção como parte da resposta
    estruturada (JSON mode ou function calling).
  - Isso elimina a manutenção do classifier e aumenta a precisão.

---
ITEM 4.3 — Relatório semanal enviado por WhatsApp sem formatação rica
---
ARQUIVO: bot-service/app/reports.py
PROBLEMA:
  O relatório semanal vai como mensagem de texto simples para o
  proprietário. Sem métricas visuais, sem PDF, sem link para o
  dashboard. O cliente não consegue ter uma percepção clara do valor
  que o agente está gerando.

SOLUÇÃO:
  - Estruturar o relatório com seções claras usando formatação
    WhatsApp (*negrito*, _itálico_):
    * Total de leads novos na semana
    * Leads qualificados (interessado/quente/agendado)
    * Taxa de conversão calculada
    * Top 3 intenções da semana
    * Conversas que aguardam atendimento humano
  - Incluir no final o link direto para o dashboard:
    "📊 Ver relatório completo: https://app.atendia.com.br/[slug]"
  - Essa percepção de valor é o principal antídoto contra churn.

---
ITEM 4.4 — Não há detecção de leads que ficaram sem resposta
---
PROBLEMA:
  Se um lead enviou uma mensagem e o webhook falhou, ou a Evolution
  não entregou a resposta, o lead fica em estado de abandono sem
  que o sistema ou o proprietário saibam.

SOLUÇÃO:
  - Adicionar coluna ultima_resposta_em (DateTime) na tabela Lead.
  - Criar tarefa diária que detecta leads com ultima_mensagem recente
    e sem resposta do agente nas últimas 2 horas.
  - Notificar o proprietário via WhatsApp:
    "⚠️ O lead [número] enviou mensagem há 3h e não recebeu resposta."
  - Isso também serve como feature de "monitoramento de qualidade".

================================================================
SPRINT 5 — USABILIDADE: DASHBOARD (Operador/Cliente)
================================================================

OBJETIVO: Remover fricções do uso diário do dashboard pelo
cliente (dono do negócio).

---
ITEM 5.1 — Sem feedback visual de estado de carregamento nas páginas
---
PROBLEMA:
  As páginas de conversas, funil e insights fazem fetch da API sem
  estados de loading/error tratados de forma consistente. O usuário
  fica olhando para tela em branco se a API demorar ou falhar.

SOLUÇÃO:
  - Implementar skeleton loaders nas páginas de dados.
  - Implementar tratamento de erro com mensagem amigável e botão
    de "Tentar novamente".
  - O estado de erro deve ser distinto do estado vazio
    (ex: "Nenhum lead ainda" vs "Erro ao carregar. Tente novamente.").

---
ITEM 5.2 — Dashboard de conversas não atualiza em tempo real
---
ARQUIVO: dashboard/src/app/(dashboard)/[slug]/conversas/page.tsx
PROBLEMA:
  A lista de conversas é carregada uma vez no mount. Se um cliente
  enviar mensagem enquanto o operador está com o dashboard aberto,
  nada acontece. O operador precisa dar F5.

SOLUÇÃO DE CURTO PRAZO:
  - Implementar polling: refetch da lista a cada 15 segundos.
  - Indicador visual discreto ("Atualizado há X segundos").

SOLUÇÃO DE MÉDIO PRAZO:
  - Implementar WebSocket ou Server-Sent Events (SSE) no backend
    para notificações em tempo real quando uma nova mensagem chegar.
  - FastAPI suporta SSE nativamente via StreamingResponse.

---
ITEM 5.3 — Painel de conversa não mostra status de transbordo claramente
---
PROBLEMA:
  O status de transbordo (pausado/aguardando) existe no backend mas
  a experiência de ver e agir sobre ele no dashboard não é fluida.
  O operador precisa saber claramente quando uma conversa está pausada
  e precisa de atenção humana.

SOLUÇÃO:
  - Conversas com transbordo "pausado" devem aparecer no TOPO da lista,
    com badge vermelho "Aguardando Atendimento".
  - Conversas com transbordo "aguardando" (lead confirmou mas não foi
    aceito ainda) devem ter badge amarelo.
  - Botão de "Assumir Atendimento / Reativar Robô" visível direto
    na listagem, sem precisar abrir a conversa.

---
ITEM 5.4 — Tela de WhatsApp/QR Code sem instrução contextual
---
ARQUIVO: dashboard/src/app/(dashboard)/[slug]/whatsapp/page.tsx
PROBLEMA:
  A tela mostra o QR Code para conexão, mas não guia o usuário
  novo em como conectar. Muitos clientes de PME nunca usaram
  WhatsApp Business API e ficam perdidos.

SOLUÇÃO:
  - Adicionar um passo-a-passo numerado ao lado do QR Code:
    1. Abra o WhatsApp no seu celular
    2. Toque em ⋮ (menu) → Aparelhos conectados
    3. Toque em "Conectar aparelho"
    4. Aponte a câmera para o código QR ao lado
  - Adicionar status visual claro: "Conectado ✅" com ícone verde
    vs "Aguardando conexão ⏳" com instrução de ação.

---
ITEM 5.5 — Não há como o operador enviar mensagem manual pelo dashboard
---
PROBLEMA:
  Quando o transbordo é ativado, o operador precisa abrir o WhatsApp
  no celular para responder ao lead. Isso quebra o fluxo e o histórico
  da conversa no dashboard fica desatualizado.

SOLUÇÃO:
  - Adicionar campo de texto + botão "Enviar" na tela de histórico
    de conversa.
  - O backend recebe a mensagem, chama a Evolution API para enviar,
    e salva no banco como mensagem do tipo "operador" (distinto de
    "usuario" e "agente").
  - Isso mantém o histórico completo e permite que o operador trabalhe
    100% pelo dashboard.
  - DETALHE: Só deve ser possível quando o transbordo está "pausado"
    para aquela conversa.

================================================================
SPRINT 6 — USABILIDADE: ONBOARDING E ADMINISTRAÇÃO
================================================================

OBJETIVO: Melhorar a experiência de ativação de novos clientes
e tornar a operação da plataforma sustentável sem intervenção
manual constante.

---
ITEM 6.1 — Criação de empresas é 100% manual via admin_api
---
PROBLEMA:
  Para ativar um novo cliente, o operador precisa:
  1. Chamar POST /api/admin/empresas via Postman/cURL
  2. Configurar Evolution manualmente
  3. Explicar ao cliente como usar o dashboard
  Isso não escala além de 10-20 clientes.

SOLUÇÃO:
  - Criar página de admin interna (protegida por ADMIN_TOKEN via cookie
    HttpOnly, não localStorage) com formulário de criação de empresa.
  - Campos: nome, slug, e-mail admin, senha inicial, telefone WhatsApp,
    telefone proprietário, template de nicho, valor mensalidade, dias trial.
  - Após criação, o sistema envia e-mail de boas-vindas com credenciais
    (integração com SendGrid ou SMTP simples).
  - Isso reduz o tempo de ativação de 30 minutos para 2 minutos.

---
ITEM 6.2 — Primeira configuração do agente é confusa
---
PROBLEMA:
  O cliente acessa o dashboard pela primeira vez e a página de
  configurações não tem estado "vazio" amigável. Se a config JSONB
  estiver vazia, campos ficam sem valores e o cliente não sabe
  o que preencher.

SOLUÇÃO:
  - Criar um "Assistente de Configuração" de 3 etapas no primeiro acesso:
    ETAPA 1: Identidade do Agente (nome, cargo, empresa)
    ETAPA 2: Base de Conhecimento (horários, serviços, preços — em
             formato de texto livre para facilitar)
    ETAPA 3: Conectar WhatsApp (QR Code integrado)
  - Após completar as 3 etapas, o agente já está funcional.
  - Usar localStorage ou campo na tabela Empresa (onboarding_completo:
    Boolean) para não mostrar o wizard novamente.

---
ITEM 6.3 — Não há página de listagem de empresas para o admin
---
PROBLEMA:
  O admin_api tem GET /admin/empresas, mas não há interface web para
  isso. O operador da plataforma precisa chamar a API manualmente para
  ver o estado de todos os clientes.

SOLUÇÃO:
  - Criar rota /admin (fora do dashboard de empresa) com:
    - Lista de todas as empresas com status (ativo/inativo/trial)
    - Dias restantes de trial para cada empresa
    - Botões de ativar/desativar e "Entrar como empresa" (impersonate)
    - Total de leads e mensagens por empresa (indicador de engajamento)
  - Proteger a rota com ADMIN_TOKEN armazenado em cookie HttpOnly
    (não em localStorage como está o JWT de empresa).

---
ITEM 6.4 — Logs de DEBUG em produção
---
ARQUIVOS: bot-service/app/agent.py, dashboard_api.py, whatsapp_service.py
PROBLEMA:
  Vários print() e logger.info() com "DEBUG" no nome estão espalhados
  no código e vão para produção:
    print(f"DEBUG PROMPT -> Nome: {nome_agente}...")
    print(f"DEBUG WHATSAPP -> Base URL extraída: {base}...")
    print(f"DEBUG API -> Enviando config para {empresa.nome}: {config_data}")
  Isso polui os logs e pode vazar dados de clientes.

SOLUÇÃO:
  - Substituir todos os print() por logger.debug().
  - Configurar o nível de log via variável de ambiente:
    LOG_LEVEL = os.getenv("LOG_LEVEL", "INFO")
    logging.basicConfig(level=getattr(logging, LOG_LEVEL))
  - Em produção, LOG_LEVEL=INFO oculta todos os DEBUG automaticamente.
  - Em desenvolvimento, LOG_LEVEL=DEBUG mostra tudo.

PONTOS FORTES DO PROJETO (que valem ser mantidos):
- Arquitetura multi-tenant com isolamento por empresa_id está correta.
- O padrão de debounce de mensagens (buffer.py) é inteligente e
  resolve bem o problema de mensagens fragmentadas no WhatsApp.
- O sistema de transbordo humano (pausado/aguardando/reativar) é
  uma feature diferenciada e bem implementada no backend.
- O uso de JSONB para configuração dinâmica é a escolha certa para
  suportar múltiplos nichos sem migrar o banco a cada novo cliente.
- APScheduler já integrado é uma base sólida para automações futuras.
- A estrutura de rotas do Next.js com [slug] dinâmico está bem pensada
  para um produto multi-tenant.

- agent-old.py na pasta app/ deve ser removido do repositório.
- context.py e events.py estão vazios — remover ou documentar intenção.
- migrate_db.py e migrate_user.py são scripts avulsos — considerar
  adotar Alembic para migrações versionadas e rastreáveis.
- O pool do banco (pool_size=20, max_overflow=30) é generoso demais
  para um único worker Uvicorn. Revisar conforme a escala crescer.
