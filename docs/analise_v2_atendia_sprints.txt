PARTE 1 — ESTRATÉGIA DE PRECIFICAÇÃO (pergunta do dev)
================================================================

PERGUNTA: "Como cobrar do cliente se cada um tem um perfil de uso
diferente de LLM? Uma loja com 20 mensagens/dia vs 100 mensagens/dia?"

RESPOSTA ESTRATÉGICA COMPLETA:

O problema que você identificou é real e é chamado no mercado de
"custo variável não repassado". Existem três modelos usados por
SaaS que têm esse perfil (custo de IA por transação):

---
MODELO A — PLANO FLAT COM LIMITE DE CONVERSAS (RECOMENDADO AGORA)
---

Como funciona:
  Você não precisa expor tokens para o cliente. Você vende
  "conversas atendidas por mês" como unidade de valor.
  O cliente entende "conversa" — não entende "token".

Exemplo de tabela de planos:

  STARTER   — R$ 197/mês — até 500 conversas/mês
  PRO       — R$ 397/mês — até 2.000 conversas/mês
  ILIMITADO — R$ 697/mês — sem limite (uso justo)

  (conversa = 1 lead ativo que enviou pelo menos 1 mensagem no mês)

Por que funciona para você:
  - 1 conversa média = ~10 trocas de mensagens = ~2.000 tokens.
  - gpt-4o-mini custa ~$0,60 por 1M tokens de input + $2,40 output.
  - 500 conversas × 2.000 tokens = 1M tokens → custo real ~$0,60–3,00.
  - Com R$ 197, sua margem bruta é confortável mesmo no pior caso.
  - 2.000 conversas no PRO → custo real ~$3–12. Com R$ 397, seguro.

O plano ILIMITADO existe para ancorar o PRO como "razoável" e
para clientes grandes que já têm tráfego alto. O "uso justo"
(fair use policy) é uma cláusula nos termos que permite suspender
clientes abusivos (ex: > 10.000 conversas/mês no plano Ilimitado).

Implementação no banco:
  Adicionar em Empresa:
    plano (String): "starter" | "pro" | "ilimitado"
    limite_conversas_mes (Integer): 500 | 2000 | 99999
    conversas_mes_atual (Integer): contador do mês corrente
    data_reset_contador (DateTime): primeiro dia do próximo mês

  Em pipeline.py, antes de processar:
    Se conversas_mes_atual >= limite_conversas_mes:
      Enviar mensagem ao lead: "Nosso atendimento automático está
      temporariamente indisponível. Entre em contato pelo telefone."
      Notificar proprietário via WhatsApp sobre limite atingido.
      Retornar sem chamar a OpenAI.

---
MODELO B — REPASSE DE CUSTO COM MARKUP (para clientes GRANDES)
---

Como funciona:
  Você rastreia os tokens consumidos por empresa (já sugerido na v1)
  e cobra uma taxa fixa + markup sobre o custo real de IA.

Exemplo:
  Taxa base: R$ 197/mês (cobertura do serviço/plataforma)
  + Custo de IA: tokens consumidos × taxa unitária com markup de 3×

Por que NÃO é o modelo ideal para agora:
  - Exige faturamento variável (boleto muda todo mês).
  - Clientes de PME odeiam conta variável — causa cancelamentos.
  - Complexidade de billing muito maior.
  - Só vale para clientes enterprise (franquias grandes, redes).

Conclusão: use o Modelo A agora. Adicione o Modelo B como
"Plano Enterprise" sob consulta quando tiver clientes grandes.

---
MODELO C — COBRANÇA POR LEAD GERADO (performance)
---

Como funciona:
  Você cobra por lead que atingiu um determinado stage
  (ex: "agendado" ou "qualificado"), não por mensagem.

Por que NÃO recomendo agora:
  - Você não controla a qualidade do produto/atendimento do cliente.
  - O cliente pode manipular os stages para não pagar.
  - Muito difícil de auditar sem integração com CRM externo.
  - Adequado apenas para nichos de alto ticket (imobiliárias premium).

---
RECOMENDAÇÃO FINAL PARA IMPLEMENTAÇÃO:
---

  1. Agora: Implementar Modelo A (flat por conversas)
     com 3 planos (Starter, Pro, Ilimitado).
  2. Médio prazo: Rastrear tokens por empresa internamente
     (não expor ao cliente) para calibrar sua margem real.
  3. Longo prazo: Oferecer Modelo B como "Enterprise" para
     clientes com > 5.000 conversas/mês.

O rastreamento de tokens (descrito na Sprint 3 abaixo) serve
para você, o operador da plataforma, entender sua margem real —
não precisa ser exposto ao cliente final.

ITEM 2.1 — Painel Admin autentica via localStorage (problema novo)
---
ARQUIVO: dashboard/src/app/(admin)/admin/page.tsx

O admin token fica no estado React (useState) e é enviado no
header de cada requisição. Isso é aceitável para tokens não-sensíveis,
mas o fluxo de impersonation tem um problema grave:

CÓDIGO PROBLEMÁTICO (handleImpersonate):
  localStorage.setItem("atendia_token", access_token);
  localStorage.setItem("atendia_slug", slug);
  window.open(url, "_blank");

O impersonation grava o token JWT de um CLIENTE no localStorage
da aba do admin. Se o admin tiver outras abas abertas da plataforma,
o token pode interferir na sessão delas. Além disso, o localStorage
persiste até ser limpado — o token fica "esquecido" no navegador.

CORREÇÃO:
  - Para impersonation, passar o token como parâmetro de URL
    (token de uso único, expira em 5 minutos):
    window.open(`/${slug}?impersonate_token=${access_token}`, "_blank")
  - A página do cliente lê o parâmetro, grava temporariamente,
    e limpa a URL imediatamente após.
  - OU: abrir a aba e usar postMessage para transferir o token
    sem expô-lo na URL.

ITEM 2.2 — Middleware de isolamento não cobre path params
---
ARQUIVO: bot-service/app/middleware.py

O middleware verifica empresa_id injetado via QUERY STRING:

Mas não verifica empresa_id injetado via PATH PARAM

AÇÃO:
  - Adicionar comentário claro no middleware explicando que a
    proteção de path params é responsabilidade do Depends() de
    cada endpoint, não do middleware global.
  - Auditar todos os endpoints do dashboard_api.py para confirmar
    que todos usam Depends(obter_empresa) corretamente.
  - Verificar se algum endpoint aceita empresa_id como path param
    sem validar contra o token JWT.

ITEM 2.5 — Webhook loga o RAW DATA completo em INFO
---
ARQUIVO: bot-service/app/main.py

  logger.info(f"RAW DATA: {json.dumps(data)}")

O payload do webhook da Evolution pode conter o base64 completo
de um áudio (centenas de KB de string). Isso vai para o log JSON
estruturado, que pode ser enviado para sistemas de log externos.
Além do volume, dados de áudio de clientes ficam nos logs.

CORREÇÃO:
  # Não logar o RAW DATA em INFO. Usar DEBUG no máximo.
  # Em DEBUG, truncar o base64 para não poluir:
  if logger.isEnabledFor(logging.DEBUG):
      safe_data = {k: (v[:50] + "...[truncado]" if isinstance(v, str) and len(v) > 50 else v)
                   for k, v in data.items()}
      logger.debug(f"RAW DATA (truncado): {json.dumps(safe_data)}")

ITEM 3.3 — Controle de limite de conversas no pipeline

No início de processar_webhook(), antes de qualquer chamada à IA:

  # Verifica se a empresa está dentro do limite do plano
  if empresa.plano != "ilimitado":
      # Verifica e reseta o contador mensal se necessário
      agora = datetime.utcnow()
      if not empresa.data_reset_contador or agora >= empresa.data_reset_contador:
          empresa.conversas_mes_atual = 0

          Lead.empresa_id == empresa.id,
          Lead.telefone == telefone,
          Lead.criado_em >= empresa.data_reset_contador - timedelta(days=31)
      ).first()

      # Conta conversas únicas no mês (leads únicos ativos)

ITEM 6.3 — Migração manual no init_db() acumulando
---
ARQUIVO: bot-service/app/database.py
As migrações manuais via ALTER TABLE estão crescendo dentro do
init_db(). Isso funciona mas é frágil — se uma migração falhar
no meio, o banco fica em estado inconsistente sem rollback.

RECOMENDAÇÃO: Adotar Alembic para migrações versionadas.
  pip install alembic
  alembic init migrations
  alembic revision --autogenerate -m "add plano e contadores"
  alembic upgrade head

Isso resolve o problema de deploys com migrações parciais.

---
ITEM 6.4 — Pool do banco superdimensionado para 1 worker
---
ARQUIVO: bot-service/app/database.py
  engine = create_engine(DATABASE_URL, pool_size=20, max_overflow=30)
  
Com 1 worker Uvicorn (default em produção), esse pool cria
conexões desnecessárias. Revisar para:
  pool_size=5, max_overflow=10
  
Aumentar apenas quando escalar horizontalmente (múltiplos workers).

---
ITEM 6.5 — Dois health checks conflitantes em main.py
---
ARQUIVO: bot-service/app/main.py

Existem dois endpoints com comportamento diferente:
  @app.get("/health")  ← verifica banco e openai key (correto)
  @app.get("/")        ← retorna apenas {"status": "online"} (legado)

Manter apenas o /health e redirecionar / para ele, ou remover
o endpoint / para não ter dois comportamentos diferentes.
